# Arena improvement watcher

`jevops.improvement_service` is a persistent, bounded supervisor targeting the
**existing Lean Refactor Arena**. It collects development evaluations, asks the
in-tree `llm_router` for experiments, trains the existing sparse autoencoder,
and tests exact Python edits in isolated workers. It does not implement a new
natural-language autoformalization benchmark.

## Experiment and promotion boundary

1. Freeze the Python runtime, corpus, project bindings, and seed reports.
2. Collect development proofs and evaluation observations in SQLite. Imported
   results and outer-loop `ok` flags are hints, never fresh proof admission.
3. Request one bounded JSON experiment through an explicitly attested route.
4. Run proposed Python and training only in rootless Docker: no network, no
   credentials or checkout mounts, read-only root, bounded CPU/RAM/PIDs/output,
   and a temporary filesystem. Only JSON crosses the worker boundary.
5. Recompute checkpoint cross-entropy and cosine similarity using the frozen
   host implementation. Never accept scores supplied by experimental Python.
6. Require a shorter proof with the exact original theorem statement. Screen
   and confirm with fresh native Lean processes on **every pin of that problem**,
   in both branch orders (two screening and three confirmation repetitions).
   The `strict-dual-v1` objective requires both token and raw-heartbeat improvement,
   without expanded axioms. Heartbeat limits are not measurements.
7. For Python/checkpoint deployment, also compare old/new output on three fresh
   randomized stdlib canaries using native Lean, requiring nonregression.
8. Atomically promote the proof policy and managed Python/checkpoint generation.
   Subsequent sandbox workers consume that generation. The dirty checkout is
   **never overwritten**, and candidate Python is never imported on the host.

Proof receipts, rejected outputs, training checkpoints, and code generations
are generated by the program and retained. The model supplies hypotheses and
small proposals, not large reports. Source-bound policy entries are reusable
proposals; they do not replace verification in downstream evaluators.

## Training and Python actions

The router can request `candidate`, `rules`, `explore`, `train`,
`python_experiment`, or `wait`. For example:

```json
{"action":"train","train_steps":8,"learning_rate":0.04,"hypothesis":"Distill shorter development proofs."}
```

`python_experiment` takes `changes: [{path, old, new}]`, a `strategy`, and optional
`train_steps`/`learning_rate`. Each edit must match exactly one nonempty substring;
at most three edits are allowed, and the resulting Python must parse. Editable
modules are `logic_refactor.py`, `folds.py`, `tactics.py`, `proof_slicing.py`,
`autoencoder.py`, `autoencoder_training.py`, and `nca.py` under `jevops/`.
The verifier, scorer, worker entrypoint, supervisor, corpus, and tests are not
editable. The older `code_proposal` action remains review-only.

Before routing, frozen source analysis builds a bounded menu of unverified
portable rewrites, local deletions, and historical endpoints. `explore` selects
one exact `proposal_id`; the host reconstructs the proposal from its own menu.
Previously evaluated sources are excluded. Diffs, token deltas, and potential
single-span training support are analysis, not proof or heartbeat claims.
Mixed actions such as `train` plus `rules` are rejected rather than silently
ignoring the rules. Compiler diagnostics and no-gain token counts survive prompt
compaction even when the full proof is too large to include.

Training performs actual `LeanIRAutoencoder.train_batch` updates, using bounded
development teacher pairs. Historical teachers need consistent source-bound
native report claims; that makes them eligible training data, **not freshly
authenticated successes**. Fully verified shorter development proofs also become
teachers when they miss the stricter heartbeat promotion objective. Both
endpoints require complete fresh screening coverage and no axiom growth; failed
or missing samples cannot teach. Neither the 12 excluded Arena problems nor random canary examples
are sent in training requests.

The learned span-edit head is explicitly enabled. The host mines the grammar
from development endpoints before training; experimental Python cannot alter
that grammar. Teacher support is reported explicitly. If none of the shortened
endpoints is representable, training abstains with `NO_SUPPORTED_REWRITE_TEACHERS`
and the router is directed toward collecting verified local edits instead.
Distant coordinated edits are **not** split into invented verified intermediate
teachers. The existing graph-composition learner likewise requires checked
intermediate states; it does not solve this coverage gap automatically.

Training steps are bounded to 1–32 and learning rate to 0.0005–0.25. The checkpoint
must change. Training cross-entropy must decrease; train/canary cosine may not
drop by more than 0.01, and canary cross-entropy may not rise by more than 0.01.
Comparisons use the deployed checkpoint, not a moving experimental baseline.
An experimental checkpoint may continue training before it earns deployment;
lower losses alone cannot promote a proof, checkpoint, or Python generation.
Additionally, edit-head cross-entropy must decrease and expected cosine loss
must not increase relative to the pre-update checkpoint, with identical grammar
and supported-teacher coverage. This comparison is separate from the deployed
checkpoint reconstruction/canary gates.

The IR decoder's convenience theorem header is not used as a benchmark
statement: only its predicted proof body is rebound to the frozen statement.
This does not establish validity; intake and native Lean checks still apply.

## Connect an existing outer loop

The watcher runs independently. To feed additional evaluations from
`jevops.outer.run_steps`, use its existing `on_step` injection point:

```python
from pathlib import Path
from jevops.improvement_service import Config, ImprovementHook
from jevops.outer import run_steps

hook = ImprovementHook(Config.load(Path("/absolute/path/to/config.json")))
try:
    result = run_steps(**existing_run_arguments, on_step=hook.on_step)
finally:
    hook.close()
```

Rows may supply `last_lake`, or `payload.lake`, containing dictionaries with
`name`, full `source`/`proof`/`tactics`/`body`/`src`, `ok`, `tokens`, and
`raw_heartbeats`. Only configured development names are ingested. Full proofs
are retained up to the byte bound; oversized data is rejected, not silently
truncated. All observations are explicitly unverified hints.

`hook.candidates(record)` returns source-bound proposals for a **fresh verifier**.
`hook.deployed_generation()` returns code/checkpoint data with
`sandbox_required=True`; do not import those modules into an outer-loop host.
Attaching the hook to another process is explicit, not automatic process patching.

## Start, inspect, and stop

Bootstrap creates a new snapshot and optionally a transient user systemd service:

```bash
python -m jevops.improvement_bootstrap \
  --repo /path/to/JevOps \
  --volume-config /path/to/existing/preparation.json \
  --corpus /path/to/arena/corpus.jsonl \
  --projects /path/to/prepared-projects.json \
  --seed-report /path/to/native-development-trial.json \
  --development CallElimCorrect.extractedOldExprInVars \
  --elan-home /path/to/prepared/elan \
  --docker-socket /run/user/1000/docker.sock \
  --docker-image sha256:YOUR_LOCAL_IMMUTABLE_IMAGE \
  --provider codex_cli --model gpt-5.6-luna \
  --interval 120 --router-budget 8 --native-budget 200 --start
```

Repeat `--projects`, `--seed-report`, and `--development` as needed. All other
corpus names become the excluded holdout partition. Bootstrap prints the unit
and configuration path and writes a machine-generated `launch.json` containing
the exact frozen command. It does not build missing dependencies or pull images.

The first continued Arena attempt used 24 native processes but all failed to

were accepted. Its 60-request reserve remains spent. After staging the runtime,
four additional native smoke checks all verified; those four requests are also
charged to the same 200-request budget.

At budget exhaustion the service remains in `BUDGET_EXHAUSTED`, polling without
further model/native work. Guard failures stop it. Budgets do not reset on
restart. This is a transient user service, not an installed boot-time daemon.
A failed unchanged native control sets `ENVIRONMENT_FAILED`, preventing more
paid proposals in that runtime. Repair requires an explicitly resumed snapshot.
Proposal deduplication is scoped to the runtime digest, so an infrastructure
repair can legitimately retry a proposal without erasing prior failed evidence.
To upgrade code, stop the old service, use the same bootstrap options plus
`--resume-config /old/run/config.json`, and start the new snapshot. This copies
the ledger, checkpoints, and spent budgets; old artifacts remain untouched.
An explicitly authorized extension uses `--extend-router-budget N` on resume
(at most 32 additional calls). It records old/new limits and preserves spent
counters. Native budgets, routing, and data partitions cannot change on resume.

## Storage, interpretation, and limitations

The watcher uses the existing capped **50 GB** preparation volume. It retains
all build caches and receipts, refuses work below reserved free-space headroom,
and limits its state footprint. It never deletes caches or enlarges the cap.
The runtime is additionally copied read-only through `arena_prepare.stage_imports`
into the **existing external setup reservation** (32 MB maximum reservation per
runtime, also bounded by remaining setup headroom). This is necessary because
UID-65534 cannot read an owner-only FUSE mount. Snapshot bytes are reverified
after copying. FUSE is not remounted with `allow_other`, source permissions are
not relaxed, and the worker UID/capabilities remain unchanged. Both copies are
retained and staging metadata is recorded in `launch.json`.
Ephemeral worker containers and scratch files are cleaned up; prepared build
caches and durable experiment evidence are not.

The frozen scorer and isolated workers reduce reward-hacking opportunities;
they are not a proof against every possible exploit. The router is a trusted
provider invoked in read-only mode; prompt-level holdout exclusion is not an
adversarial filesystem sandbox for the router itself. Edited Python receives
stronger worker isolation. Operating-system/container security is still trusted.

The three canaries are **synthetic stdlib regression checks**, not a full-15
Arena validation or evidence of generalization. The 12 excluded Arena problems
are not automatically scored by this watcher. A confirmed local promotion is
not an official high score; `official_score` remains null. A separate frozen,
all-pin full-15 evaluation is required for that claim.

NCA code is eligible for experiments, but this does not by itself implement or
demonstrate successful NCA training. The initial real training runs lowered loss
without earning a promotion. A separate Docker smoke test exercised an exact
Python edit without deployment; its receipt is `python-edit-smoke.json` in the
retained `improvement-watch-usqmn2ud` run.
A separate native canary-gate smoke run compared identical old/new outputs on
three fresh canaries: all 12 native executions verified. Its independent
36-request reservation and complete trials are in that run's `canary-gate-smoke.json`.
This tests the gate, not an improvement or the held-out Arena problems.
